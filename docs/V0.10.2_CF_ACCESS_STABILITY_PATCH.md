# v0.10.2-beta CF Access Stability Patch

## Summary

Seattle OpenClaw is exposed through Cloudflare Access at `act.hnsnowground.cfd`.
Web AI Assistant calls Seattle through the OpenAI-compatible legacy SSE path:

- Provider: `openclaw-seattle`
- Runtime base URL: `https://act.hnsnowground.cfd/v1`
- Execution mode: `legacy`
- Production model verified: `openclaw-seattle / openclaw-seattle-glm5.1`

When `act.hnsnowground.cfd/*` was protected by Cloudflare Access, requests from
Web AI Assistant to `https://act.hnsnowground.cfd/v1/*` initially received HTTP
302 responses that redirected to the Cloudflare Access login page. The browser
then surfaced either an empty response placeholder or a provider error instead
of a Seattle OpenClaw answer.

## Why the Base URL Stays on `act.hnsnowground.cfd`

The Seattle runtime is intentionally configured as:

```text
https://act.hnsnowground.cfd/v1
```

It should not be changed to `ai.hnsnowground.cfd`. The `ai.hnsnowground.cfd`
host serves the Web AI Assistant application shell and API routes, not the
Seattle OpenClaw OpenAI-compatible upstream. Probing `ai.hnsnowground.cfd/v1/*`
returns the wrong application surface or Web AI Assistant auth responses rather
than the Seattle OpenClaw gateway.

## Worker Service Token Headers

The Worker injects Cloudflare Access service-token headers only for Seattle
OpenClaw upstream URLs whose hostname and path match:

```text
https://act.hnsnowground.cfd/v1
https://act.hnsnowground.cfd/v1/*
```

The injected headers are:

```text
CF-Access-Client-Id: env.ACT_CF_ACCESS_CLIENT_ID
CF-Access-Client-Secret: env.ACT_CF_ACCESS_CLIENT_SECRET
```

The implementation deliberately does not affect:

- `hill.hnsnowground.cfd`
- Hillsboro Native Bridge routes
- Hillsboro legacy `/v1/*`
- OpenAI, GLM, Kimi, Workers AI, or other ordinary providers

If either secret is missing, the Worker preserves the original request behavior
instead of throwing during header construction. OpenClaw upstream redirects are
handled manually so Cloudflare Access 302 responses cannot be silently followed
into an HTML login page and misreported as an empty model response.

## Incorrect Cloudflare Access Policy

The failing Access configuration mixed browser login and machine access in the
same ordinary Allow policy:

```text
Policy action: Allow
Include:
  - Email
  - Service Token
```

With that configuration:

- `curl` with service-token headers still returned HTTP 302.
- Worker requests still returned HTTP 302.
- The redirect target was `cloudflareaccess.com`.
- Cloudflare Access metadata showed `service_token_status=false`.
- The Service Token page showed `Last Seen: Not Seen Yet`.

Those signals mean Cloudflare Access did not accept the service token for the
application policy, even though the Worker request included the service-token
headers.

## Correct Cloudflare Access Policy

The working configuration keeps browser and machine access in separate policies
under the same Access Application:

```text
Destination: act.hnsnowground.cfd/*
```

Policy 1, browser users:

```text
Action: Allow
Include: specified email address
```

Policy 2, machine access:

```text
Action: Service Auth
Include: Service Token -> Seattle act
```

The two policies do not need a manually configured OR relationship. Cloudflare
Access evaluates the Service Auth policy for machine requests and the Allow
policy for browser login.

The destination may later be narrowed to `act.hnsnowground.cfd/v1*` for the
Seattle API while leaving browser-protected tools under a separate application
or policy, but the validated production fix used `act.hnsnowground.cfd/*`.

## Validation Signals

Before the Access policy fix:

```text
HTTP 302
Location: https://...cloudflareaccess.com/cdn-cgi/access/login/...
service_token_status=false
Service Token Last Seen: Not Seen Yet
```

After splitting the policies, direct service-token probing reached the upstream
OpenClaw authentication layer:

```text
HTTP 401
Content-Type: application/json
Body: {"error":{"message":"Unauthorized","type":"unauthorized"}}
Set-Cookie: CF_Authorization=...
```

The `401` JSON response is the expected proof that Cloudflare Access allowed the
machine request through and the request reached Seattle OpenClaw's own
authentication layer. It is no longer a Cloudflare Access login redirect.

Final production validation through Web AI Assistant:

- Model: `openclaw-seattle / openclaw-seattle-glm5.1`
- Latency: `9919ms`
- Fallback count: `0`
- Result: production test passed
- No HTTP 302
- No `cloudflare_access_blocked`
- No empty reply placeholder

## Secrets and Safety

The Worker secret names are:

```text
ACT_CF_ACCESS_CLIENT_ID
ACT_CF_ACCESS_CLIENT_SECRET
```

Do not record the real Client ID or Client Secret in:

- Git
- Documentation
- Logs
- D1
- Worker responses
- Frontend bundles
- Test snapshots

If a Service Token value is exposed, rotate it immediately in Cloudflare Zero
Trust and update the Worker secrets with `wrangler secret put`.
