# v0.13.7-beta: OpenClaw dual transport integration

Date: 2026-10-17

Production Worker version verified before tagging:
`42b82713-e194-448a-a9e4-554af5600642`

This release adds Hillsboro as the second managed OpenClaw instance while
preserving the existing Seattle integration and classic model behavior. The
browser selects an instance, Agent, and optional base model. The Worker decides
which trusted server-side transport to use for that instance.

## Completed changes

- Added `Hillsboro OpenClaw` to the server-controlled instance allowlist. The
  saved instance configuration is migrated once without rewriting classic
  provider/model data.
- Added a Hillsboro Gateway catalog endpoint with its own D1 cache key,
  five-minute freshness window, forced refresh, and `fresh`, `stale`, or
  `error` state. Seattle and Hillsboro never share catalog cache entries.
- Added server-side validation of Hillsboro Agent IDs and base model IDs before
  a Bridge task is submitted.
- Extended Bridge task submission with `selection_mode`, `base_model_id`, and
  validated Codex run controls. Classic Bridge calls retain the previous task
  shape and behavior.
- Added per-turn Hillsboro model routing. Agent default selection resolves the
  current default from the Gateway catalog; an explicit base model applies only
  to that turn.
- Preserved conversation context across Hillsboro turns by creating an
  isolated session for each turn and forking it from the previous completed
  turn. The Agent's persistent default and shared session state are not
  modified.
- Added requested, resolved, and actual model IDs to Bridge task status and
  result normalization. The actual model is read from assistant history
  metadata when available.
- Added GPT-only Effort and Fast controls. Supported Effort values are `low`,
  `medium`, `high`, `xhigh`, `max`, and `ultra`; speed is `standard` or `fast`.
  The controls are validated on both Worker and Bridge paths and are ignored
  for non-OpenAI models.
- Updated the model chooser and model settings UI for Seattle and Hillsboro.
  The run controls are compact, and OpenClaw instance management now appears as
  a provider-style card below `OpenAI 兼容` with add, edit, and delete actions.
- Disabled Wrangler preview URLs so production secrets are not exposed through
  a lingering preview deployment.

## Transport design

### Seattle: Legacy SSE for chat, Gateway WSS for catalog

Seattle chat continues to use the OpenAI-compatible HTTP endpoint at the fixed
server-side target `https://act.hnsnowground.cfd/v1`.

- Each Agent turn sends `model: openclaw/<agentId>`.
- `x-openclaw-model` is omitted for Agent default selection.
- `x-openclaw-model` contains the validated base model ID only for an explicit
  override.
- The response is streamed to the page as SSE using the existing request and
  history path.
- The Gateway bearer token and Cloudflare Access service token remain Worker
  secrets. They are not returned to, stored by, or sent from the browser.

Seattle directory synchronization is separate from the chat transport. The
Worker connects to the protected `/gateway-ws/catalog` route, completes the
signed Gateway handshake with an `operator.read` device, and calls
`agents.list` plus `models.list` with `view: "configured"`. The route preserves
WebSocket Upgrade and proxies to the main Gateway listener at
`127.0.0.1:18789`. `GET /v1/models` is not used as a base model directory.

### Hillsboro: Bridge tasks and callbacks for chat and catalog mediation

Hillsboro keeps the existing Bridge task, streaming, callback, recovery, and
attachment behavior. The browser never selects a protocol. The Worker pins the
Hillsboro instance to its allowlisted Bridge configuration and authenticates
with a server-side Bridge token.

The Bridge was upgraded to `14.3-run-controls`:

- `GET /v1/openclaw/catalog` reads the real Gateway `agents.list` and
  `models.list(view: "configured")` results.
- `POST /v1/openclaw/tasks` validates the requested Agent and model against the
  current catalog before creating a turn.
- Agent default selection resolves to the Agent's current Gateway default.
- Explicit selection creates that turn's Gateway session with the requested
  model.
- A new unique session key is used per turn. When earlier context exists, the
  session is forked from the previous completed turn so the conversation is
  retained without changing shared or persistent defaults.
- Results expose the requested, resolved, and actual execution model so model
  routing can be checked independently from the UI label.

The verified Hillsboro Agent IDs are `main`, `glm5-2`, `glm51`, and
`kimi-for-coding`. The selectable base models at release time are:

- `openai/gpt-5.6-terra`
- `openai/gpt-5.6-sol`
- `openai/gpt-5.6-luna`
- `openai/gpt-6-astra`
- `zai/glm-5.0-turbo`
- `zai/glm-5.1`
- `zai/glm-5.2`
- `kimi/kimi-for-coding`

`openai/gpt-5.5`, `openai/gpt-6-sol`, `openai/gpt-6-luna`, and
`openai/gpt-6.1-sol` are filtered from Hillsboro and rejected as overrides.
The first is retired; the other three could not be materialized with the
installed OpenClaw version and current subscription route.

## Problems encountered and resolutions

### Seattle did not expose the Gateway WebSocket

The original Nginx configuration exposed only `/v1/`, so WebSocket probes
reached HTTP redirects or 404 responses and never received
`connect.challenge`. A dedicated Upgrade-only `/gateway-ws/catalog` location
was installed in `/etc/nginx/conf.d/act.conf`, validated with `nginx -t`, and
proxied to `127.0.0.1:18789`. Cloudflare Access remained in front of the route,
and the Worker received a device identity scoped only to `operator.read`.

### Access headers were previously scoped to `/v1/*`

The catalog WSS path could not rely on the existing HTTP helper. A separate,
host-scoped WebSocket connection injects `ACT_CF_ACCESS_CLIENT_ID` and
`ACT_CF_ACCESS_CLIENT_SECRET` only for `act.hnsnowground.cfd`. Gateway bearer
authentication remains separate and server-side.

### Hillsboro Bridge had no real directory API

Five candidate read-only HTTP paths returned 404. Runtime registry data was
insufficient because it was not the Gateway's configured base model catalog.
The Bridge now performs the real read-only Gateway RPC calls and exposes only
normalized public catalog fields through its authenticated endpoint. The
Worker applies an independent Hillsboro cache and never treats `/v1/models` as
the base model directory.

### Bridge originally accepted only `agent_id`

Changing an Agent's persistent default would have affected other sessions and
could not provide per-turn switching. The Bridge now resolves and validates
the selection, creates a unique Gateway session with the selected model, and
forks from the previous completed turn when context must continue.

### Initial session strategies failed

Gateway rejected incognito sessions with `incognito sessions are web-only`.
Regular isolated sessions fixed that restriction. A later retry reused a
label and failed with `label already in use`; UUID-based session keys and
idempotency labels removed the collision. Temporary restart windows also
produced local port connection failures; installation now waits for the
systemd service to become active and verifies `/health` before catalog checks.

### Retired GPT model silently fell back

Hillsboro previously advertised `openai/gpt-5.5`. A request could resolve to
that model while the runtime executed `zai/glm-5`, which made the UI appear to
lie about the active model. The VPS configuration was updated to supported GPT
models, the retired and route-incompatible IDs are filtered and rejected, and
Bridge results now record the actual execution model. Real calls verified the
four listed OpenAI models without rerouting or fallback.

## Compatibility and security

- Classic mode data, classic OpenClaw entries, ordinary providers, existing
  conversations, and stored per-message model information are preserved.
- Each new send resolves its current selection, allowing ordinary models,
  Seattle, and Hillsboro to be selected on successive turns.
- Instance targets and credential bindings are fixed server-side. A browser
  cannot submit an arbitrary upstream URL, Bridge address, or secret name.
- Catalog and instance management endpoints remain behind application
  authentication. Catalog responses use `Cache-Control: no-store` and expose
  only normalized public fields.
- Gateway bearer tokens, Bridge tokens, and Cloudflare Access credentials stay
  out of page state, API responses, logs, and browser requests.
- Removing an instance deletes only the web application's connection record;
  it does not change a VPS Gateway, Agent, or model configuration.
